# JSON 格式正確，內容仍然可能錯

API 回傳了所有必要欄位，還是可能教給學習者錯誤的定義。我在意這個差別，因為它會影響生成內容拿到使用者面前之前，究竟該檢查什麼。

自己的兩個專案剛好有不同的做法。

[TOEFL Vocab 的 Gemini helper](https://github.com/asdc163/toefl-vocab/blob/f62588e785d07d948d625f225ff3b8eb3c7daada/lib/gemini.ts)在請求裡帶 response schema，再取出回覆文字、解析 JSON。這讓呼叫端有一致的起點，但程式沒有另外對每個回傳欄位做完整的執行期驗證。

[CareLens 的 Claude helper](https://github.com/asdc163/carelens/blob/828ec6d9ea46ba61b1ff8d9d4fe82706d62ae4a2/src/lib/claude.ts)多做了一步，用 Zod 解析結果。欄位型別不符可以被拒絕，看起來合理、內容卻錯的值仍可能通過。另外，沒有設定 key 時，這個 helper 會回傳固定的 mock 資料。因此，拿到成功回覆本身，還不能證明圖片辨識真的執行過。

## 每一層檢查回答不同問題

連線檢查能知道供應商有沒有回應。JSON 解析檢查格式，runtime schema 檢查結構。它們都無法判斷單字與定義是否相符，或辨識結果是否真的出現在圖片裡。

單字功能需要把生成卡片和要求的單字、來源內容放在一起看。圖片辨識則逐欄對照原圖，保留人工修正。mock 與真實供應商的執行紀錄也要分開。

模型自己給的 confidence 同樣需要檢驗。在沒有拿它和實際錯誤對照以前，我會把它當成另一個輸出欄位。

## 試行以前，我會怎麼測

先準備一般輸入、缺少資料、內容矛盾和供應商故障的案例。每筆保留來源、預期行為與實際回覆，把內容錯誤和解析失敗分開看，再確認使用者是否能恢復流程或修正結果。

產品決定要等到這裡才有依據。解析失敗少，能支持介面格式這一層；要讓功能承擔更多責任，還得看語意錯誤與使用者能不能完成工作。

這是我提出的評估方式，不是模型實測結果。文中的固定版本程式於 2026-10-28 檢視，沒有為了這篇筆記呼叫供應商。
